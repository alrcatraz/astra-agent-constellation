# 拓扑与角色

## 1. 角色总表

| 角色 | 实现示例 | 职责 | 数量 | 部署位置 |
|:-----|:---------|:-----|:-----|:---------|
| **编排者**（Orchestrator） | Hermes Agent（当前）；也可是 DSH 编排者版 / 其他满足编排职责的 Agent（2026-08-20：同一角色可适配不同 Agent，可担任≠必须担任） | 唯一用户交互入口；任务拆解；调用执行者；验收；与用户共同确认规划与细节 | 1 | 主工作机 |
| **执行者**（Executor） | OpenCode（headless）与 dsh 均为推荐执行者（当前实际部署=dsh） | 在指定平台上完成编码/构建任务；永不直接与用户对话；只通过编排者汇报 | 按需（见下） | 承担开发/编译/训练/测试功能的机器 |
| **看护者**（Guardian） | Hermes Agent 或独立栈（平台不绑定，以故障域隔离为约束） | 维护除自己以外所有智能体的更新、恢复、健康检查；经独立渠道可被用户直接访问 | 0–1 | **独立物理机**（不与编排者同机） |
| **工具门禁**（Tool Gate） | 如 Astra AI Gate | 统一鉴权与审计所有智能体对工具服务的访问 | 1 | 基础设施层 |

## 2. 职责边界（MUST）

- **MUST**：编排者是唯一与用户交互的智能体。执行者与看护者的一切汇报都经由编排者转达，不直接接触用户。
- **MUST**：执行者只部署在承担开发/编译/训练/测试功能的机器上。不得为「整齐」而在无工作负载的设备上部署执行者。
- **MUST**：看护者与编排者不得部署在同一台物理机上（详见[双星模式](06-gemini-pattern.md)）。
- **MUST**：工具门禁是智能体访问共享工具服务的唯一入口（详见[基础设施共用](03-tool-sharing.md)）。
- **SHOULD**：编排者直接执行短任务（运维、单文件小改、并行子任务），仅在长编码任务与跨机构建-修复循环场景调用执行者。

### 2.1 任务分流表（编排者路由决策）

用户提出需求后，编排者按下表决定走哪条调用链——**分流发生在拆任务之前**，是编排者每次面对用户需求时的固定决策步骤：

| 任务特征 | 调用链 | 依据 |
|:--|:--|:--|
| 运维操作（服务重启、状态查看、配置小改） | 编排者直接执行 | 01 §2 SHOULD（短任务） |
| 单文件小改 / 文档修改 / 并行子任务 | 编排者直接执行 | 01 §2 SHOULD |
| 长编码任务（多文件、跨模块） | 编排者 → 执行者（同机或跨机） | 01 §3.1/3.2，task-brief 契约 |
| 跨机构建-修复循环（编译失败→改→再编译） | 编排者 → 执行者（构建机） | 01 §3.2，04 §2 MUST |
| 需要健康检查 / 版本升级 / 恢复服务 | 编排者 → 看护者（通过共享事实层间接触发） | 01 §3.3，06 §6，08 章 |
| 需要验证结果 / 变更审批 | 编排者验收（重跑命令 + diff 审查），不委派 | 04 §2 MUST，05 §3 |
| 已授权且需持久状态的并行/依赖子任务集 | 复用统一委派协调语义（DAG 台账）调度 worker，不按子任务开新会话 | ADR 0007，见 §2.2 |

- **MUST**：分流是编排者的决策，不自动执行——短任务也需确认任务性质后再走对应链路。
- **MUST NOT**：把「该编排者直接执行的短任务」拆给执行者（增加延迟与上下文损耗）；把「该走执行者的长任务」自己硬啃（违反 01 §2 SHOULD）。
- **SHOULD**：拿不准时，按「用户在场 → 编排者直接执行」优先，用户明确要求长编码/构建任务时才拆执行者。
- **超时与常驻（ADR 0007 §9）**：派发走执行者时，**超时分三层**——①收活窗口（秒级，接单判定，失败重派）/ ②存活检测（进度信号，失联进恢复判定不杀工作）/ ③工作生命周期（task brief 写 Budget，可协商、到期是决策点非死刑），**不再用单一派发窗口同时承担三种语义**。执行者以 **ACP server 形态常驻**（跨智能体协作要求），编排者跨任务经 `session/load`/`resume` 接回，握手只在会话建立时付一次。
- **持久执行原语（ADR 0007 §9.6）**：派发前先问「这份工作要不要活得比发起它的会话/进程更久」——要，则**MUST** 用持久原语（定时任务会话 / 后台常驻进程）承接，**MUST NOT** 用进程本地的派生子会话（发起方退出即丢工作）；「持久」只解决存活，层③ Budget 与资源硬顶照旧。

## 2.2 委派协调语义（统一任务委派基座）

> 借鉴社区局部任务团队实践，本架构把「任务分解、依赖、attempt、恢复、会话治理」抽象为**传输无关的统一语义**（ADR 0007），由编排者会话的协调上下文承载，**不新增组织角色**。协调者就是编排者本身，不产生第二个全局编排实体。

- **MUST**：spawn / fork / ACP / A2A 是**传输方式**，统一的是任务生命周期语义；按接缝的关系模型选传输（见 ADR 0006 / 0007），不按任务量堆叠协议。
- **MUST**：任务状态（DAG 进度、attempt、依赖、恢复）由共享 state store 承载，**不存放于 A2A 对话历史或 ACP session**——状态/会话分离是缓解 A2A 次数与 ACP 垃圾会话的根本手段。
- **MUST**：worker 可用状态与任务完成状态分离；主体已完成但未收尾时先走恢复判定，不直接判 idle / failed。
- **MUST NOT**：为实现局部任务协作而新增「队长/成员」等组织角色；协调上下文属编排者，局部协作不放宽全局权限边界。
- **MUST NOT**：为「接收执行者/对等 Agent 的消息」创建一次性 session；结果经既有通道/共享状态交付（见 12 章）。

详细状态机、attempt、lease、recovery、会话复用与垃圾回收规则见 [ADR 0007](references/0007-delegation-semantics-and-session-governance.md)。

## 3. 调用链路

> 协议选型边界（ADR 0006）：**编排者/看护者 → 执行者的派活走 ACP**（host→agent 主从语义）；
> **编排者 ↔ 看护者的状态交换走共享事实层**（异步 git，无实时协议）；
> **多个编排者之间的对等协作（未来）走 A2A**；
> **与团体外智能体/团体的对外互操作走 A2A + ANP 分层**（任务对话 + 身份信任，
> 见 [12 跨 Agent 协作与互操作](12-cross-agent-collab.md)）。本节 3.1–3.3 描述当前
> 实现形态：**ACP 化已落地**——task-brief 经 ACP content blocks 传递（映射见
> 10 ACP 内容映射）；此前的 `opencode run` 字符串契约是过渡
> 形态，已被 ACP 取代（见 ADR 0006「被否决的选项」）。

### 3.1 编排者 → 执行者（同机）

```bash
# 执行者以 ACP server 形态运行（OpenCode / dsh 均为推荐执行者，不分先后）
node <DSH_ROOT>/apps/cli/lib/bin.js --profile acp --patch executor/<OVERLAY>.yml
```

派发由编排者的 ACP client 发起（建会话 → `session/prompt` 携带 task-brief 的
content blocks），执行者在自己的工作目录中运行；会话可跨任务接回
（`session/load`/`resume`，见 ADR 0007 §9）。

### 3.2 编排者 → 执行者（跨机）

```bash
# 同一条 ACP 启动命令，用 ssh 包装成远程 transport（协议不变，只换传输）
ssh <USER>@<BUILD_HOST> "cd <PROJECT_DIR> && node <DSH_ROOT>/apps/cli/lib/bin.js --profile acp --patch executor/<OVERLAY>.yml"
```

> 注意：本机场景去掉 ssh 自环；跨机场景才用 ssh。大文件传输（如容器镜像）优先流式管道而非 scp（已知教训：`/tmp` 是 tmpfs 易满，scp 大 tar 会卡死）。

### 3.3 编排者 → 看护者

看护者不是实时在线对话对象。编排者与看护者通过**共享事实层**（git 仓库、健康检查状态文件、agent 注册表）间接同步，不建立编排者→看护者的实时消息通道。（例外：看护者自身保有独立交流渠道，供编排者失联时用户直接访问——见[双星模式](06-gemini-pattern.md)第 3 节。）

## 4. 每个角色的「智能」边界

| 角色 | 有权限知道的 | 无权限知道的 |
|:-----|:-------------|:-------------|
| 编排者 | 全部：用户偏好、记忆、会话、凭证引用 | — |
| 执行者 | 任务 brief、项目 AGENTS.md、相关代码、验证命令 | 用户私人记忆、凭证值（只通过环境变量注入的引用） |
| 看护者 | 所有智能体的部署定义、版本、健康状态、注册表 | 各智能体的会话内容与私有记忆 |
| 工具门禁 | 鉴权信息、审计日志 | 工具服务的内部实现细节 |

## 5. 扩展与收缩

- **MAY**：在出现真实构建-修复循环痛点后，才部署新的执行者（如构建机、训练工作站）。先痛点后部署，不预先铺开。
- **SHOULD**：执行者只部署在承担开发、编译、训练、测试等功能的机器上；不得为「整齐」而在无工作负载的设备上部署执行者。
- **MUST NOT**：不得引入执行者之间的直接通信。执行者之间若有协作需求，必须经由编排者编排。
- **MUST NOT**：不得为了「多智能体」而增加编排者数量。编排者唯一；执行者数量随工作负载按需增长，没有硬性上限。

## 6. 失败模式

| 故障 | 影响 | 恢复 |
|:-----|:-----|:-----|
| 编排者机器宕机 | 用户失去主入口 | 看护者（独立机器）依据 agent 注册表恢复编排者 |
| 执行者机器宕机 | 编码/构建任务中断 | 编排者重新调度到另一执行点或降级为直接执行 |
| 工具门禁宕机 | 所有智能体无法访问共享工具 | 编排者直接连接本地服务（降级路径），门禁恢复后回归 |
| 看护者机器宕机 | 更新/恢复职责中断 | 编排者临时接管看护职责（非对称降级），待看护者恢复 |
