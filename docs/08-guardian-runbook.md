# 看护者操作手册（Guardian Runbook）

> 本文档是[双星模式](06-gemini-pattern.md) §6 职责清单的**可执行落地**：把「更新 / 恢复 / 同步 / 报告」四条原则拆成逐步操作。原则见 06 章，操作见本文——**原则被改写时追加 ADR，操作随环境更新**。
>
> 看护者是 headless 维护者，遵循与执行者同一套纪律（见[纪律传导](04-harness.md)）：**技术路线行不通时停下汇报，不自行换方案**；验证命令写死，编排者重跑才算数。所有操作落 git 历史（可审计）。
>
> 关键信息一律**引用而非复制**：目标机器的地址走凭证库 `devices.<key>.network` 与 `connection.paths`，恢复流程走注册表 `restart` 引用（`doc-ref`），不在此重复任何值。

## 0. 操作前通用步骤（MUST）

1. **读注册表**：`agent-registry/registry.yaml` 中目标智能体的 `version` / `health_check` / `restart` 字段——本次操作的目标版本与验证方式**以注册表为准**。
2. **记当前状态**：注册表变更 + git status 留痕，作为操作前基线。
3. **备份**：对目标做可回滚备份（配置/数据/依赖清单任一形式）。
4. **定验证命令**：从注册表 `health_check` 或任务 brief 取**写死的命令与预期结果**，不临时发挥。

## 1. 更新流程（职责①）

> 适用：编排者、执行者之外的所有智能体版本升级（06 §6.1）。编排者/执行者的升级由编排者自身执行，看护者不越权。

### 步骤

1. **确认目标版本**：注册表记录 → 与上游发布对比 → 确定升级目标。
2. **盘点本地改动**（升级前必做，见 §1.1）：`git status --short` + `git stash list` + 本地补丁清单 → 逐项登记分类。
3. **备份**：目标配置 + 数据 + 当前版本记录 + **本地改动快照**（可回滚点）。
4. **对照上游**：读 changelog / release notes，逐补丁判断是否已被上游吸收（见 §1.1 决策矩阵）。
5. **git 拉取**：`git fetch` + `git checkout <目标版本 tag/commit>`（或按项目 AGENTS.md 的升级流程）。
6. **依赖更新**：按项目锁文件更新（npm ci / uv sync / 系统包），**不升级未声明版本**。
7. **重放本地改动**：按 §1.1 决策结果恢复应保留的改动（完整/部分/不恢复），**逐项验证恢复后有效性**。
8. **运行验证**：执行注册表 `health_check` 命令，**预期结果以注册表为准**。
9. **通过才收工**：
   - ✅ 验证通过 **且** 所有保留补丁验证有效 → 更新注册表 `version` 字段 → commit（含升级前后版本对比 + 补丁处置记录）→ 报告。
   - ❌ 任一验证失败 → **回滚**到备份点 → 重跑验证 → 汇报失败证据 + 根因初判，**不自行换升级路线**（04 §2 停止条件）。

### 1.1 本地改动评估（升级完成判定的关键）

本地改动不是「升级的阻碍」也不是「一律保留」——是**需要逐类决策的资产**。**升级完成 = 版本到位 且 每个本地改动都明确了处置并验证有效**。

**分类**（按改动来源，不是按文件）：

| 类别 | 特征 | 处置原则 |
|:--|:--|:--|
| **A. 实例专属信息** | 该设备/实例的配置值：主机名、端口、路径、实例专用参数、部署定义 | **必须保留**；注意上游格式变更时需**适配后重放**（值不变，位置可能变） |
| **B. 修复补丁** | 修复上游 bug 的本地改动（如 Matrix E2EE 补丁）；特征：补丁说明引用 issue/故障现象 | **逐补丁对照上游**（见决策矩阵）：上游已修复 → 不恢复；部分修复 → 恢复缺口；未修复 → 完整恢复 |
| **C. 功能/实验增强** | 本地新功能或实验性改动，上游没有 | 评估价值：保留（验证有效）或放弃（记录原因）；**不默认保留** |

**B 类决策矩阵**（逐补丁对照上游 changelog / 源码）：

| 上游状态 | 处置 | 验证 |
|:--|:--|:--|
| 已原生实现（吸收） | **不恢复**本地补丁，改用上游实现 | 验证上游实现覆盖原故障（如 E2EE 收发正常） |
| 部分吸收 | **恢复剩余部分**（只补上游没做的缺口） | 验证缺口场景有效 |
| 未修复 | **完整恢复**本地补丁 | 验证原故障场景有效（补丁标记可 grep） |

**恢复后验证（MUST）**：每个保留的补丁/改动都必须有**可执行的有效性验证**（补丁标记 grep、故障场景复现测试、冒烟命令），**不能只看 `git status` 干净——「文件在」≠「补丁有效」**。恢复项验证全部通过，升级才算完成。

### 失败分支

| 失败点 | 处理 |
|:--|:--|
| git 拉取失败 | 检查网络/远端可达性；不可达则记入报告，**不猜测原因强行重试 N 次** |
| 依赖更新破坏兼容 | 回滚依赖到备份点，汇报冲突依赖与建议方向 |
| 补丁重放冲突（stash pop 冲突） | 手工 3-way 合并：**保留上游重构 + 重放本地缺口**；合并后查无冲突标记、逐项验证有效 |
| 验证命令本身报错（非目标故障） | 停下，汇报原始输出——**不得改命令或预期来制造通过**（05 §3） |

## 2. 恢复流程（职责②）

> 核心场景：健康检查失败 → 按注册表 `restart` 引用恢复。这是双星模式的根本目的（06 §7：主星宕机时看护星依据注册表恢复主星）。

### 步骤

1. **发现异常**：健康检查 cron 触发告警（或主星主动上报）。
2. **查注册表**：读目标智能体的 `restart` 字段 → 解析 `doc-ref`（恢复流程文档位置）与依赖的 `device-ref`（机器地址，走凭证库解析）。
3. **确认影响面**：目标宕机影响哪些依赖（查 01 章拓扑）；**判断是否为级联故障**（多智能体同时失败时先恢复基础设施层）。
4. **执行恢复**：按 `restart` 引用文档逐步执行——**恢复步骤本身也是写死的命令序列**，不临场发挥。
5. **验证恢复**：重跑该智能体的 `health_check`，通过才算恢复完成。
6. **记录与报告**：恢复耗时、执行了什么、验证结果 → 注册表 + 报告。

### 失败分支

| 失败点 | 处理 |
|:--|:--|
| 恢复流程文档缺失/过期 | 停下，汇报缺失项——**不凭记忆编恢复步骤**（凭证纪律同样适用：值一律走引用） |
| 恢复后 health_check 仍失败 | 升级为**主星宕机场景**：检查主星 → 主星也宕则按 §2.1 处理；单目标反复失败则停下汇报，不无限重试 |
| 目标机器不可达（网络层） | 按凭证库 `connection.paths` 多路径优先级切换通道；全路径失败则停下汇报 |

### 2.1 主星宕机恢复（双星模式验收场景）

1. 看护星自身健康确认（先保证恢复者自身存活）。
2. 读注册表主星条目 → `restart` 引用 + `deploy_def`（部署定义位置）。
3. 按 `deploy_def` 重建/恢复主星（同框架独立升级轨道，见 [ADR 0001](references/0001-agent-platform-selection.md)）。
4. 验证主星 `health_check` 通过 + 主星能读取注册表（恢复后自检）。
5. 报告：宕机时长、恢复动作、验证证据、根因初判（供复盘）。

## 3. 同步流程（职责③）

> 拉取 dotfiles、技能仓库、知识库更新；检查 AGENTS.md 漂移。

1. **拉取清单**：按 02 章同步分层定义的各仓库（dotfiles / 技能 / 知识库 / 文档站）。
2. **逐仓拉取**：`git fetch` + fast-forward（**不用 force-push 覆盖**；发现分叉 → 停下汇报，不自行 rebase 吞并）。
3. **漂移检查**：对比各仓 AGENTS.md / dotfiles 与真源（git diff）：
   - 无差异 → 记录「同步正常」。
   - 有差异 → **停下汇报**差异内容与来源判断（真源改动未同步？还是本地被改？），**不自行回滚或覆盖**。
4. **注册表联动**：同步结果反映到注册表（若有版本变化）。

## 4. 报告流程（职责④）

1. **周期性报告**：默认静默（06 §6.4）——维护结果写入报告通道（06 §3 独立渠道），无异常不打扰。
2. **异常告警**：健康检查失败 / 恢复不成功 / 同步漂移 → **立即**通过 06 §3 渠道告警，内容含：对象、现象、已执行动作、验证结果、下一步建议。
3. **报告格式**：时间 / 操作类型 / 目标 / 动作摘要 / 验证结果 / 证据（日志或命令输出）/ 决策记录（改了什么、为什么、替代方案）。

## 5. 纪律对照（每次操作自检）

- [ ] 技术路线行不通 → 停下汇报，不自行换方案（04 §2）
- [ ] 验证命令失败 → 报原始输出 + 根因初判，不改命令凑绿（05 §3）
- [ ] 范围外需求 → 记入报告，不顺手扩大（04 §2）
- [ ] 缺信息/权限/资源 → 停下问编排者，不靠猜
- [ ] 凭证值只引用不复制（L5：技能/文档不出现任何值）
- [ ] 升级时本地改动按类处置（A 实例专属保留 / B 修复补丁对照上游 / C 增强评估），保留项逐项验证有效（§1.1）
- [ ] 所有操作落 git 历史（可审计）
